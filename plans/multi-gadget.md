# Multi-Gadget Workspaces: Analysis & Plan

## Current state (one paragraph)

Today "workspace" = "gadget" = one Overseer DO. The DO holds: one code history (`code`/`snapshots` collections replaying into a Y.Doc whose single unnamed root map is filename→Y.Text), one `gatekeepers` table (sequential IDs from `nextGatekeeperId`, with `bindingName` stored *on* the gatekeeper record + unique `byBindingName` index), one hard-coded `"gadget"` facet, chats/actions/hooks/sharing/observers all keyed without a gadget dimension, and loopback props that identify targets by `overseerId` alone. Blueprints snapshot the whole doc + named bindings; the frontend's `Overseer` stub *is* the gadget's identity everywhere.

## Core architectural decisions

**1. Workpieces: a workspace contains numbered "workpieces" in a single ID namespace.** A workpiece is a thing the user (or agent) is working on within the workspace. In v1 there are two types — **gadgets** and **gatekeepers** — but the concept is designed for more:
- Gatekeepers that display a UI in the workspace panel (self-configuration, or e.g. a Google Doc gatekeeper previewing the doc) — especially useful once agents can create new external objects (e.g. a new Google Doc as a chat output).
- Mounted sub-objects of a gatekeeper (e.g. the GitHub gatekeeper checks out a branch, mounted into the workspace as a file tree the regular code editor — and the agent's file tools — operate on directly).
- Simple markdown/rich-text documents probably do *not* need a type: they're expressible as a trivial gadget (blueprint) whose `client.js` renders `README.md`.

Namespace mechanics:
- **One shared sequential ID counter** for all workpieces. For now it keeps its existing storage name `nextGatekeeperId` (renaming would require a storage migration for no functional gain) — this is a documented wart, cleaned up in a possible later migration.
- **Separate `gadgets` and `gatekeepers` tables for now**, both allocating from the shared counter. IDs are unique across both, so references are bare numbers and facet name prefixes (`gatekeeper${id}`, `gadget${id}`) can never collide. Merging the two tables into one `workpieces` table is a candidate future migration.
- New `gadgets` collection: `{id, title, bindings, created, ...}`. A `WorkpieceId` type alias (number) in workshop-shared makes the concept legible in the API.
- **Capsules and ambient gatekeepers are workpieces** (they're gatekeeper records and always were in this ID space). They are hidden from the workpiece picker UI for now; eventually we'll likely display capsules at least while the chat thread containing them is open.

**2. Yjs: per-workpiece named roots, not map-of-maps.** Each gadget's files live in `ydoc.getMap(rootNameFor(id))` — the decimal workpiece ID as the root name, except the migrated legacy gadget keeps the unnamed root `""` (zero migration for existing docs). Root IDs are sparse (the namespace is shared with gatekeepers); that's fine — the registry, not the doc, is the enumeration source of truth. Reasons to prefer named roots:
- Map-of-maps requires re-parenting existing Y.Text instances (Y types can't move once integrated — you'd clone content, and you'd still need a new root name since the current root already holds files, so it buys nothing).
- Enumerating Y.Doc roots via `doc.share` is hacky; the doc only needs deterministic per-workpiece addressing.
- Named roots can never be deleted from a Y.Doc, but since IDs are never reused, a deleted gadget just leaves an empty tombstone map — acceptable.
- The whole-doc update-log persistence model (`code` collection, snapshots, `subscribeToCode`/`updateCode`, per-chat proposed-changes updates) **doesn't change at all** — updates naturally span roots.
- Future payoff: any workpiece type can own a files root (e.g. a mounted git branch), and the code editor / agent file tools / sync machinery work on it unchanged.

**3. Bindings: move binding names off `GatekeeperRecord` into the gadget record, as binding-edge records.** Each gadget's binding list is expected to stay small, so rather than a separate collection, each record in the `gadgets` collection carries a `bindings: Record<name, BindingRecord>` map, where `BindingRecord = {target: WorkpieceId, blueprintAnnotation?: BlueprintBindingAnnotation}`. (A bare-number value was considered, but the blueprint annotation belongs to the binding *edge*, not to the gatekeeper — two gadgets binding the same gatekeeper can annotate it differently for their respective blueprints — so an edge record it is. `blueprintAnnotation` accordingly moves off `GatekeeperRecord` too; overseer.ts:147-161.) The `bindingName` field and unique `byBindingName` index on `gatekeepers` (overseer.ts:508-515) go away. This directly gives you "two gadgets bind the same gatekeeper", and — thanks to the shared namespace — gadget-to-gadget bindings later are just a binding whose target ID happens to be a gadget.
- Consequence: reverse lookups ("which gadgets bind gatekeeper X" — needed for orphan detection and observer scoping) become a scan over the `gadgets` collection. Fine, since gadget counts are small.
- Policy scope for shared gatekeepers (resolved): **auto-approval rules stay workspace-wide per gatekeeper** (`${gatekeeperId}:${tag}` keying unchanged) — approving an action kind approves it no matter which gadget invokes it. **Actions and hooks record no binding name**; they identify the gatekeeper and display its resource title (binding names are per-gadget and ambiguous for a shared gatekeeper). **Removing a connection in the UI merely unbinds** (deletes the binding entry from that gadget); the gatekeeper record survives, possibly orphaned — surfacing and deleting orphaned gatekeepers is a follow-up change.

**4. Chats are workspace-scoped.** A chat's proposed changes are whole-doc Yjs updates and can therefore touch multiple gadgets — this is a feature ("build me a slide deck gadget and wire the viewer gadget to it" in one thread). Chat storage needs no re-keying. The gadget dimension is added to *what the agent edits and runs*, not to the chat.

**5. Zero gadgets is a valid state; no auto-created initial gadget.** Once multiple gadgets are supported, a workspace starts with *no* gadgets, and the agent explicitly creates the first one via `createGadget` just like any other. (Transitional exception: until the agent has the `createGadget` tool — phasing steps 2 vs. 3 — workspace creation keeps auto-creating an initial gadget so the product stays functional.)

**6. `defaultGadgetId` for back-compat (annoying but unavoidable).** Because the ID namespace is shared, the migrated legacy gadget is *not* ID 0 — it's allocated from wherever the workspace's counter stands. Every "defaults to gadget 0" device therefore becomes "defaults to the workspace's `defaultGadgetId`": a singleton set whenever a gadget was *auto-created* (lazy migration of existing workspaces, and workspaces created during the transitional phase). Workspaces created after the agent gains `createGadget` never set it — there, gadget references are always explicit. Absent-`gadgetId` resolution (replayed tool calls, persisted `OverseerRestoreParams`, flat env compat) goes through `defaultGadgetId`; if it's unset, absent references are an error. **`defaultGadgetId` is never reassigned**: if that gadget is deleted, absent-ID references fail with an explicit "gadget was deleted" error rather than silently retargeting old tool calls and persisted callbacks at some other gadget.

**7. Explicit schema version; migration runs before *any* entrypoint.** "No gadget registry exists" is not a usable migration trigger — zero gadgets is a valid migrated state (new workspaces, or after deleting the last gadget). A `schemaVersion` storage singleton records migration state explicitly. And migration must be gated on every path into the DO, not just `open()`: the Overseer also wakes via constructor-driven agent-turn restoration (overseer.ts:879-900), hook deliveries, and `restore()`-based persistent callbacks (overseer.ts:3804-3817). Run migration in the constructor under `blockConcurrencyWhile()` (or an equivalent ensure-migrated gate that every entrypoint passes through).

## Change inventory by area

### workshop-shared/api.ts
- `WorkpieceId` type alias (number) documenting the shared namespace.
- `Overseer` gains gadget-list surface: `listGadgets()` (or fold into `GadgetMetadata`/`subscribeToMetadata` so the sidebar updates live), `createGadget(...)`, `deleteGadget(id)`. (Post-review: `createGadget(title, chatId?)` — creation with a chat open is provisional to that chat, recorded via a new `createdGadgets` field on the existing `changes` message type; `WorkpieceSummary.chatId` exposes pending status to the UI. See Q15.)
- Gadget-scoped methods get a **`GadgetClient` sub-capability**: `getUiBundle`, `connectToGadget`, per-gadget binding listing/management, title, per-gadget blueprint export. **`GadgetClient` and the existing `GatekeeperClient` become two subinterfaces of a common base, `WorkpieceClient`** (shared identity/lifecycle surface: `getId`, `remove`, title/description-ish metadata; type-specific operations stay on the subinterfaces). This matches the codebase's capability style, keeps `UseOverseerInterface`'s compile-time default-deny clean, and gives a natural home for future per-gadget sharing and future workpiece types. Workspace-level things stay on `Overseer`: code sync (one doc), chat, sharing, actions, blueprint listing.
- Binding management moves off `GatekeeperClient`: `setBindingName`/`setSuggestedBindingName` — and `get`/`setBlueprintAnnotation`, since the annotation now lives on the binding edge — become operations on `GadgetClient` (or gain a gadget parameter). "Remove binding" (unbind from one gadget) becomes a `GadgetClient` operation, distinct from destroying the gatekeeper itself.
- Chat streaming events `setActiveFile` and `toolCallTarget` (api.ts:1703-1711) gain a `workpieceId`: a chat can edit multiple gadgets, and a filename alone (e.g. `client.js`) no longer identifies where streaming edits are happening.
- `GadgetMetadata` becomes workspace metadata + per-gadget summaries (id, title).
- Blueprint types are already gadget-shaped and need **no format change** (a blueprint's code snapshot is a single-root doc; `snapshotCode` just reads from the right root). `.gadget` archives stay compatible.
- Note for the future: using Yjs as the blueprint content format has become nonsensical — both creation and consumption make a whole-tree copy, losing any change history. At some point we should plan to move to a different format (a simple zip, or full-on git). Not part of this change.

### Overseer runtime (overseer.ts)
- Facet naming: the facet name is a storage key, so **the migrated legacy gadget keeps the name `"gadget"`** for backward compatibility; all other gadgets get `` `gadget${id}` `` (1315, 1943) — collision-free with `gatekeeper${id}` thanks to the shared counter. Use a helper analogous to (or shared with) `rootNameFor()`. `#runningChatId` becomes per-gadget. Bonus: testing a branch of gadget A no longer aborts gadget B.
- `loadGadgetWorker(gadgetId, chatId?)`: read files from the gadget's root map; loader cache key gains the gadget dimension (1249).
- `getEnvForLoader(...)` takes a gadgetId and builds env from that gadget's binding map. `env.GADGET` (the gadget's self-stub) is of questionable value going forward — it was always primarily intended for agents in `executeCode`, and agents now get a totally different env; there's little use case for gadget self-callback. Keep it in the gadget worker's env for back-compat with existing gadget code, but de-emphasize it.
- **Agent-spawner env allowlists are temporarily dropped.** The existing filter is a flat binding-name allowlist (`spawnerConfig.env`, overseer.ts:1036-1078) that doesn't map onto the new `env.gadgets[id]` structure, and spawned chat context records no originating gadget. Rather than invent structured allowlist semantics now, spawned agents lose allowlist support in this change (acceptable temporary regression while in alpha); the redesign lands as a follow-up, probably after named env vars settle how workpieces map to names.
- **`executeCode`'s `ctx.restore()` targets the first gadget, for now.** Today persistent stubs sealed inside executeCode restore to the sole gadget facet (overseer.ts:3305-3317, 3804-3832). A general design — letting executed code choose which gadget owns each persistent callback/hook — is tricky enough to be a follow-up change. For now, restore is assumed to target the workspace's first gadget (`defaultGadgetId` when set, else the lowest-numbered gadget; error if there are none), documented as a known limitation.
- Loopback props that identify a *gadget* gain `gadgetId`: `GatekeeperLoopbackProps` (caller attribution + the `GADGET` binding), `GadgetTailLoopbackProps`, `AgentSelfLoopbackProps`/`CodeModeLoopbackProps` as needed for caller attribution. `AgentSpawnerBindingProps` does **not** gain a gadgetId — it describes a gatekeeper, not a gadget.
- `OverseerRestoreParams` gains a `gadgetId` property — **optional, resolving to `defaultGadgetId` when absent**, because instances are already persisted in the wild (associated with installed hooks).
- `bumpVersion()` aborts only the affected gadget's facet (naming a binding on gadget A shouldn't restart gadget B); code commits that touch multiple gadgets' roots abort each affected one (derivable from the Yjs update, or conservatively abort all).
- `BoundHookRecord` gains `gadgetId` for **bookkeeping only** — its `callback` already encapsulates `OverseerRestoreParams` pointing at the correct gadget, so operation doesn't need it; but we want it to display which gadget a hook belongs to and to delete a gadget's hooks when the gadget is deleted. (Someday the callback could be unwrapped to get this info, but no API for that exists today.)
- `ActionRecord` does **not** gain a `gadgetId`. Instead, `GatekeeperCaller`'s `type: "gadget"` variant is extended with an optional `gadgetId` (optional for back-compat); `ActionRecord` already embeds `GatekeeperCaller`.
- Storage singletons: `title` becomes workspace title; per-gadget titles live in the registry. New `defaultGadgetId` singleton (decision #6). `containsRestrictedData` stays workspace-wide (consistent with workspace-wide sharing in v1). `nextGatekeeperId` keeps its name but now allocates all workpiece IDs — document the wart in a comment.

### Agent (agent.ts)
- File tools: `readFile`/`writeFile`/`editFile` gain a **separate `workpieceId` parameter** — named for workpieces, not gadgets, since these tools operate on any workpiece that owns a files root (today only gadgets; later e.g. mounted gatekeeper sub-objects). Not a path prefix, which would be ambiguous if we later support directory hierarchies within a workpiece (or access to other filesystems through these tools). The parameter is optional in the schema for replay back-compat: when absent it resolves to `defaultGadgetId` (histories from single-gadget days exist only in workspaces that have one); in workspaces without a `defaultGadgetId`, omitting it is an error that tells the agent to specify (or create) a gadget. Read-before-edit tracking becomes keyed by (workpieceId, filename). The system prompt's file list becomes grouped by workpiece.
- `describeBinding` and `saveCapsuleAsBinding` similarly gain an optional `gadgetId` (same resolution rule), since binding names are now per-gadget.
- New tool: `createGadget({title, ...})` — `title` is required (no default gadget titles; the agent always names its creations). Initially creates an empty gadget only; blueprint instantiation comes later (see phasing): copy the blueprint's file tree into the new gadget's root map; fill bindings by mapping binding names → existing workspace workpiece IDs (from capsules the agent holds — since capsules are already gatekeeper records in this workspace, binding one to a new gadget is just a binding-map entry) or by falling back to the existing `requestConnection` flow for anything it can't satisfy.
- **`createGadget` must be replay-safe.** History replay reconstructs tool outputs by re-running persisted calls (agent.ts:968-1078); a creation tool can't be re-run. The created workpiece ID is persisted as the tool's recorded result (like connection-request outcomes already are), and replay returns the recorded ID without creating anything.
- **Created gadgets are provisional to the chat, and creation is crash/retry-safe** (revised after phase 3 review; details in Q15): the tool creates the registry record marked `pending: {chatId}` and attaches the creation to the next flushed `changes` message (`createdGadgets`); `addChatMessages` stamps `pending.sequence` when that message is persisted. Crash recovery mirrors write/edit exactly: a creation in the log's tail not yet listed by any `changes` message is re-adopted by the resumed turn's replay (flushing and stamping with its next batch), while a pending record backed by nothing in the log is a crash orphan reaped by `reconcilePendingGadgets()` — so a turn that dies mid-flight can't leave a duplicate: the resumed turn either re-adopts the recorded creation or re-creates a fresh gadget (wasting only an ID, which is fine; IDs are never reused).
- Streaming edit events carry the workpiece dimension: `CodePreviewManager` / `ExecuteCodeStreamManager` emit (workpieceId, filename) so `setActiveFile`/`toolCallTarget` (see api.ts section) let the UI follow edits into the right gadget.
- Blueprint discovery tool (`findBlueprints` or similar): there is currently **no search index** — discovery is featured list + user library + bearer links. V1: expose the user's library + featured blueprints (titles/descriptions) as the searchable corpus; defer real search.
- `executeCode` env: see Q2 below.
- System prompt rewrite: "a workspace contains gadgets; each gadget has client.js/server.js; workspaces start empty and the first gadget is created with `createGadget`..." (agent.ts:152-285 is explicitly single-gadget today).

### Blueprints (server.ts, blueprint-archive.ts)
- `snapshotCode(gadgetId)` / `collectBindingMetadata(gadgetId)` (annotations now read from the gadget's binding edges); `BlueprintGadgetRecord` records which gadget it exports.
- **Root names don't transfer via Yjs updates — copy trees explicitly.** Yjs updates encode root names, and all existing archives use the unnamed root `""`; applying an archive update to a doc populates `""`, never a numeric root. So `""` stays the canonical *archive* root: export copies the file tree from `rootNameFor(gadgetId)` into a clean unnamed-root doc (`snapshotCode` already does a clean copy — overseer.ts:2934-2949 — it just gains a source root), and import copies file-by-file from the decoded archive doc's `""` root into the destination gadget's root (replacing today's direct `Y.applyUpdate` in `initializeFromBlueprint`, overseer.ts:3993-4012). Archive format and existing blueprints stay compatible.
- `newGadgetFromBlueprint` keeps creating a fresh workspace containing one gadget (unchanged externally); add an internal "instantiate blueprint as a new gadget in an existing workspace" used by the agent tool and (later) the UI. Both paths use the copy-in import.

### Sharing (sharing.ts)
- Nearly untouched for v1: roles, share keys, observers all stay workspace-scoped. `UseOverseerInterface` needs the gadget list + per-gadget `getUiBundle`/`connectToGadget` (via `GadgetClient`). Observer in-scope gatekeepers for "use" = "gatekeepers bound by any gadget" instead of "named gatekeepers" — a small change in `#inScopeGatekeepers` (now a scan over gadget binding maps).

### Frontend
- New workpiece-picker sidebar in `GadgetEditor`'s right panel (insert as the leftmost column of the panel at GadgetEditor.tsx:1001, above the tab bar), with the selected **workpiece** in URL search params (`?w=5`) alongside `?chat=`. **V1 lists only gadget-type workpieces** (capsules/ambient gatekeepers are hidden; displaying capsules when their thread is open is a future change). Hidden when there's at most one option; a zero-gadget workspace shows the chat-centric simple mode.
- Provisional gadgets (Q15): the picker shows a workpiece with `WorkpieceSummary.chatId` only while that chat is the one currently open (with some "pending" affordance). Creations are recorded on ordinary `changes` messages (`createdGadgets`), so the existing accept/revert flow covers them without special-casing; the `changes` card should additionally display any gadgets the batch created (and a creation-only batch has an empty no-op update).
- `GadgetCodeInterface` selects `getMap(rootNameFor(workpieceId))` (the selected workpiece's files root) instead of `getMap('')`; branch/streaming layering and update plumbing are unchanged (whole-doc). `FileSidebar`/`CodeEditor`/diff components unchanged.
- Editor streaming state (active file, follow-the-agent behavior) becomes keyed by (workpieceId, filename), consuming the workpiece-aware `setActiveFile`/`toolCallTarget` events — e.g. auto-switching the picker (or badging the other gadget) when the agent edits a gadget that isn't currently selected.
- `GadgetUI`/`GadgetUseView` take a gadget selector (or `GadgetClient` stub).
- `Connections` stays per-gadget: today it already shows only named bindings (omitting unnamed capsules), so it is effectively gadget-tied already; the natural extension is for the tab to show just the selected gadget's bindings. A workspace-global view of connections (including capsules) is a future change.
- `Activity`: a separate change is planned to move Activity out of the gadget editor entirely — don't touch it here; it shows the same (workspace-wide) activity regardless of the selected gadget.
- Use-role view needs the picker too (v1 shares all gadgets).

### Migration
Triggered by the `schemaVersion` singleton (decision #7) — **not** by "no gadget registry exists", since zero gadgets is a valid migrated state — and run before any entrypoint executes (constructor `blockConcurrencyWhile`, covering `open()`, constructor-driven agent restoration, hook deliveries, and `restore()` callbacks). The migration itself: allocate an ID from the shared counter for the legacy gadget (it will *not* be 0 in workspaces that have gatekeepers), set `defaultGadgetId` to it, give it the workspace title, copy each gatekeeper record's `bindingName` (+ `blueprintAnnotation`) into its binding map as binding-edge records, bump `schemaVersion`, and leave the Y.Doc alone — the gadget's record notes the legacy names (root `""`, facet `"gadget"`). No blueprint or archive migration needed.

## Resolved questions

**Q1: Named roots vs map-of-maps in the Y.Doc?**
→ **Resolved: named roots keyed by workpiece id**, with `""` serving as the legacy gadget's root. Avoids any content migration and any re-parenting of Y types; the registry in DO storage is the enumeration source of truth. (Detailed reasoning in decision #2.)

**Q2: What does `executeCode`'s `env` look like?**
→ **Resolved:** keep numeric capsule slots `env[0..N]` exactly as today (they're chat-scoped and unrelated to gadgets), and expose gadgets as structured entries — `env.gadgets[id]`, keyed by **workpiece ID** — each providing the gadget's RPC stub plus its named bindings. A workspace-global flat env would break on cross-gadget name collisions. ~~For workspaces with a `defaultGadgetId`, also flatten that gadget's bindings + `env.GADGET` at top level for prompt/replay compatibility — old chat histories contain executeCode calls written against the flat shape.~~
- **Revised during phase 3 review:** the default gadget's top-level flatten was dropped; the env contains *only* capsule slots and `env.gadgets`. Replay of old flat-shape histories is safe regardless because executeCode outputs are recorded, not re-run; the flatten bought only stylistic continuity for new code in old chats (the model self-corrects after one undefined-binding error), while costing a top-level namespace collision with any binding named `gadgets`. Descriptions of a binding now state both addressings (`env.NAME` in the gadget's own code vs `env.gadgets[id].NAME` in executeCode), which the flatten used to conflate.
- Note: per-chat envs were also considered; their persistence story would mirror per-chat code changes (record env changes in the chat log, replay to rebuild) — viable, but not what we're doing now.
- Follow-up (not this change): replace numeric addressing with agent-assigned **named env vars**, for gadgets and capsules alike.

**Q3: Are chat threads workspace-scoped or per-gadget?**
→ **Resolved: workspace-scoped** (decision #4). Cheapest (no chat re-keying) and strictly more capable — one thread can create and wire multiple gadgets. The chat pane stays where it is; only the right panel gets the picker.

**Q4: Workspace title vs gadget titles.**
→ **Resolved:** keep auto-titling the *workspace* from the first chat (overseer.ts:3114). Gadget titles need no default — `createGadget` always specifies a title — and can be renamed by the user in the sidebar. The migrated legacy gadget inherits the workspace title.

**Q5: Is the Connections tab workspace- or gadget-scoped?**
→ **Resolved: per-gadget.** The tab today already shows only named bindings (never unnamed capsules), so it's already effectively gadget-tied; extending it to show just the selected gadget's bindings is the natural continuation. A more workspace-global view of connections (including capsules) is worth designing eventually, but is left for a future change.

**Q6: How does the agent discover blueprints?**
→ **Resolved:** no search index exists; for v1, a tool returning the user's library + featured blueprints (title/description/bindings) — small corpora the model can scan itself. A real index (KV-backed or embedding search) is a separate project.

**Q7: Per-gadget API surface — optional `gadgetId` params vs a `GadgetClient` sub-capability?**
→ **Resolved: sub-capability**, as a subinterface of a common `WorkpieceClient` base shared with `GatekeeperClient` (matches the existing capability style, keeps kernel review clean, natural home for per-gadget sharing and future workpiece types). `GadgetClient` doesn't exist yet, so there's no churn in naming it under the workpiece scheme from the start.

**Q8: Gadget deletion in v1?**
→ **Resolved: yes, minimal:** remove registry entry (which carries the binding map); disable and delete hooks pointed at the gadget; abort/delete the facet; clear (not delete) the Y root. No need to protect blueprint sources — blueprints already survive source deletion via KV/R2.
- **Resurrection is accepted, and it's inert.** Under whole-doc Yjs sync, clearing a root can't stop an old client, in-flight update, or later-merged chat branch from writing content back into a tombstoned root. That's fine: the registry is the source of truth, so content in a root with no registry entry is never listed, loaded, executed, or rendered — it's dead weight in the doc, not a revived gadget. No scrubbing/rejection machinery.
- **Deleting the `defaultGadgetId` gadget never reassigns the singleton** (decision #6): subsequent absent-ID references (old replayed tool calls, persisted restore params) fail with an explicit error instead of being redirected to a different gadget.

**Q9: Action/hook attribution.**
→ **Resolved** (as detailed in the Overseer runtime section): hooks gain `gadgetId` on `BoundHookRecord` for bookkeeping (operationally the callback's `OverseerRestoreParams` already points at the right gadget). Actions are attributed by extending `GatekeeperCaller`'s `type: "gadget"` variant with an optional `gadgetId` — `ActionRecord` itself is unchanged since it embeds the caller.

**Q10: What happens to `deleteSelf`, cost tracking, `containsRestrictedData`?**
→ **Resolved: all stay workspace-level in v1.** Flag: the sharing-taint being workspace-wide means one tainted gadget locks down sharing of all gadgets in the workspace — acceptable given v1 shares the whole workspace (and the right starting point; more sophistication later), but worth documenting as a consequence users will feel.

**Q11: One "artifacts"/"workpieces" table, or separate gadget/gatekeeper tables in a shared ID namespace?**
→ **Resolved: shared counter, separate tables.** The shared namespace delivers the benefits (bare-number references, collision-free facet names, a stable substrate for future named env vars and new workpiece types) at a fraction of the kernel diff. The counter keeps its `nextGatekeeperId` storage name (documented wart). Merging the tables — and renaming the counter — is a candidate later migration.

**Q12 (review): What does sharing one gatekeeper between gadgets mean for annotations, policies, and removal?**
→ **Resolved** (details in decision #3): bindings are edge records `{target, blueprintAnnotation?}` — the annotation belongs to the edge, not the gatekeeper. Auto-approval rules stay workspace-wide per gatekeeper. Actions and hooks record no binding name — they identify the gatekeeper and display its resource title. Removing a connection unbinds only; orphaned-gatekeeper visibility/cleanup is a follow-up.

**Q13 (review): Which gadget owns persistent callbacks minted inside `executeCode`?**
→ **Resolved: punted.** A real answer (letting executed code pick the owning gadget per callback) is a follow-up change; for now `ctx.restore()` is assumed to target the workspace's first gadget (details in the Overseer runtime section).

**Q14 (review): How do agent-spawner env allowlists survive the structured env?**
→ **Resolved: they don't, temporarily.** The flat binding-name allowlist doesn't map onto `env.gadgets[id]`; spawned agents lose allowlist support in this change (acceptable in alpha), redesigned as a follow-up after named env vars settle workpiece naming.

**Q15 (review): What are `createGadget`'s semantics — and how is it crash/retry-safe?**
→ **Resolved: gadget creation within a chat is provisional, recorded as part of the chat's proposed changes, following the same accept/reject lifecycle as code edits.** A phase 3 review found the original implementation wasn't crash-safe: the gadget was durably created at tool-execution time but recorded in chat history only at step end, so a worker restart in between left an unrecorded gadget and the resumed turn could create another. The fix folds into the provisional-creation design:
- **The chat log is the source of truth; the registry record materializes it.** `GadgetRecord.pending: {chatId, sequence?}` marks a provisional gadget. The record is real so the gadget is fully functional pre-acceptance (bindings, facet, `env.gadgets`, preview from the chat branch). Log-only materialization was rejected: every registry consumer (`getGadgetRecord` and friends) would need chat context.
- **Creations ride the `changes` stream.** The `changes` message gains an optional `createdGadgets: {gadgetId, title}[]` field (a separate `gadgetCreated` message type was considered and rejected — putting creations in the proposed-changes stream means merge/revert accounting, `hasProposedChanges`, change-ID numbering, and the existing accept-changes UI all cover them with no special cases). The agent tool first flushes captured edits into their own `changes` message (the executeCode barrier pattern — so a revert at the creation never drags along earlier edits), then attaches the creation to the *next* flush — normally the turn-end flush, which fires even when no edits were captured (using a no-op empty Yjs update), batching the creation together with the new gadget's initial files. The creation shares its batch's change ID, which the tool reports exactly as writeFile/editFile do, so revert notices to the model name creations precisely.
- **Crash recovery mirrors write/edit; the stamp is atomic with the `changes` message.** The agent tool writes the record unstamped (`pending: {chatId}`); `addChatMessages` stamps `pending.sequence` in the same synchronous DO step that persists the `changes` message carrying `createdGadgets` (the output gate makes log+stamp atomic). Until that flush, the creation behaves like a pending write/edit: after a crash, replay re-adopts creations whose tool calls sit in the log unlisted by any `changes` message (set-difference rather than the edits' clear-on-any-changes rule — exact, and immune to a barrier flush landing before its step's message), so the resumed turn's next flush records and stamps them; `reconcilePendingGadgets(chatId)` reaps only unstamped records backed by *no* persisted tool call (via the full `removeGadget` path) at agent turn start and end, and defensively in merge/revert (which assert the chat idle; a spared unstamped record has no sequence and is simply not covered by a merge/revert).
- **User-initiated creations are provisional too** when a chat is open: `Overseer.createGadget(title, chatId?)` writes a `changes` message (no-op update + `createdGadgets`) and creates the stamped pending record in one synchronous step (no crash window at all on this path). Replay surfaces user creations to the model like user code edits. Without `chatId`, creation is immediate/permanent.
- **Merge/revert need no special cases.** Every stamped creation sits on an unmerged `changes` message, so `mergeChanges(chatId, mergeThrough)` promotes (clears `pending` on) creations with `sequence <= mergeThrough` and `revertChanges(chatId, revertFrom)` deletes creations with `sequence >= revertFrom` via `removeGadget()` (a pending gadget's files exist only in the chat's proposed changes, so the mainline root has nothing to clear) — the existing no-op early-returns, `hasProposedChanges` accounting, and the UI's merge-through-latest-changes behavior all just work, including for a created-but-empty gadget. `deleteChat` deletes all of the chat's pending gadgets. Ordering is sound: the creation's `changes` message always precedes any later batch touching the new gadget's root.
- **Visibility: a pending gadget exists only from its own chat's perspective.** `WorkpieceSummary.chatId` lets the UI (phase 4) show it only while that chat is open; the agent's `listGadgetInfo`/`executeCode` env/file tools/binding ops treat other chats' pending gadgets as nonexistent; `executeCodeRestoreTarget()` skips pending gadgets; "use"-role sharing (workpiece list, `getGadget`, in-scope gatekeepers) excludes them; `createBlueprint` rejects them (their mainline code is empty).

## Phasing

Each phase is a separate commit:

1. **API and storage schema changes only** — no logic implemented yet. **Review checkpoint before proceeding further.**
2. **Restore existing functionality on top of the new API and storage schemas.** Overseer internals fully support multiple gadgets at this point, and the product is fully functional again — but there is no visible difference yet for either users or agents. Workspace creation still auto-creates the initial gadget (setting `defaultGadgetId`), since the agent can't create gadgets yet.
3. **Extend the agent to understand multiple gadgets.** Add the `createGadget` tool, but do NOT support blueprints yet — the created gadget always starts empty. Stop auto-creating the initial gadget: new workspaces start with zero gadgets and the agent creates the first one explicitly (`defaultGadgetId` is no longer set for new workspaces).
4. **Extend the UI** to support picking and displaying multiple gadgets.
5. **Blueprints:** support instantiating new gadgets from blueprints, including the agent's ability to search for blueprints.

NOT implemented (left for follow-up changes):

Adding one means a creation dialog (title, plus the optional binding-name field described in Part 2), a decision about instantiating blueprints from it, and the chat-provisional-vs-permanent choice — enough complexity to be its own change.
* UI to export blueprints from gadgets other than the original/default one.
* Moving the "Activity" UI out of the per-gadget view (even though it is not gadget-specific).
* Named env vars: allowing the agent to assign names within `env` rather than use numeric IDs (both for gadgets and capsules). *(Now addressed by Part 2 below.)*
* Sharing individual gadgets without sharing all gadgets in the workspace.
* Moving the blueprint content format off Yjs (zip or git).
* Merging the `gadgets` and `gatekeepers` tables into one `workpieces` table, and renaming the `nextGatekeeperId` counter.
* New workpiece types: gatekeeper-provided UIs/previews in the workspace panel (incl. agent-created external objects), mounted gatekeeper sub-objects (e.g. checked-out git branches as editable file roots).
* Displaying capsule workpieces in the UI (e.g. while the chat thread containing them is open).
* UI for surfacing gatekeepers no longer bound to any gadget (orphans), with the option to delete them.
* General `ctx.restore()` gadget targeting in `executeCode` (per-callback owner selection); until then it assumes the first gadget.
* Redesigned agent-spawner env allowlists (structured, workpiece-aware); allowlists are non-functional until then. *(Now addressed by Part 2 below.)*
* Consider no longer auto-binding `env.GADGET`. There is no known use case for a gadget to call itself this way, it only ever made sense for executeCode, but executeCode no longer uses it (as of Part 2, below).

# Part 2: Named chat bindings

This part was added to the plan after everything above was completed (but before any of it was merged or deployed — so nothing introduced in Part 1 carries a compatibility obligation).

In the previous part of the plan, we created a concept of workpiece IDs which are exposed directly to agents. Agents have to access gadgets by their ID and named bindings as `env.gadgets[N].BINDING`. This is difficult for agents for the same reason as it is difficult for humans: the numbers have no semantic meaning and tend to blur together when there are many of them.

To that end, we now introduce a per-chat named binding map, containing both gadgets and gatekeepers. **Workpiece IDs become totally invisible to agents** — everywhere an agent currently sees or supplies an ID, it uses a name instead. (IDs remain the internal representation and the UI/API addressing; only the agent surface changes.)

## Core model

**Chat binding map** = seeded snapshot + chat-local additions, addressing `env.NAME` in executeCode:

- Binding → **gatekeeper**: loopback stub (same as a gadget binding).
- Binding → **gadget**: the gadget's **RPC stub** (`makeBindingLoopback({type: "gadget", id}, ...)`) — exactly what `env.GADGET` has always been. A gadget binding does *not* expose the gadget's own binding list; the agent reaches gatekeepers through its *own* bindings, and inspects/edits a gadget's binding list via tools and the system prompt.

**Seed layer** (persisted in `chatContext.bindings: Record<string, WorkpieceId>`, frozen at chat creation like `alwaysAvailableCapsuleIds` is today):
- Normal chats: snapshot of the workspace **default binding list** — not stored, but derived on demand from the gadgets table (see "Workspace default binding list" below).
- Spawned agents: the spawner's configured binding list — nothing else.
- Ambient gatekeepers: folded into the same map at the existing first-turn freeze point, named by the gatekeeper's `suggestedBindingName` (ambient objects are singletons and inherently not context-dependent, so the gatekeeper's suggestion is always good; no LLM).
- Pre-existing chats (created before this change) have no persisted seed; they are seeded lazily at their next turn start (see the naming chokepoint below), normal chats from the current default list and spawned chats from their frozen `spawnerConfig` (resolving an old-style allowlist the same way the migration does).

**Chat-local layer** (log-derived, replay-deterministic):
- Pasted capsules: gains `bindingName`, stamped on the persisted message; the replay text rewrite becomes `[Title](env.NAME)` instead of `[Title](env[idx])`.
- Requested connections: `bindingName` is a **required parameter of the `requestConnection` tool** — the agent knows why it is requesting the resource and picks the name itself, rather than having one derived from whatever resource the user picks at acceptance time. The name is recorded on the `connectionRequest` message at request time and is **claimed in the chat's scope from that moment** (all later naming and validation — pasted capsules, callbacks, other requests, user-created gadgets — dedupes against it), so acceptance needs no naming step; a denied request releases the name (log-derived, so replay agrees). Messages persisted before this change lack the field and are named lazily at the turn-start chokepoint like unstamped capsules (stamped alongside the existing `gatekeeperId` stamp; overseer.ts:6480 precedent for mutating the persisted message).
- `createGadget`: the name lives in the recorded tool-call input.
- User-initiated gadget creation with a chat open: the `changes` message's `createdGadgets` entries gain `bindingName`, so the creating chat picks up the name on replay.
- Agent callbacks: deterministic `PARAMS_1`, `PARAMS_2`, … (N increments per callback in the chat, derived from replay order — no stamping needed; skip any N whose name is already taken in scope). `.args`/`.resolve`/`.reject` hang off them as today.

**Agent-facing terminology: drop "capsule".** Since every resource now gets a binding immediately upon introduction, agent-facing text (system prompt, tool descriptions, injected messages) speaks only of "bindings" — a pasted resource or accepted connection is simply "a new binding in your env". The word "capsule" is still used as internal terminology (`CapsuleSpecifier`, `CapsuleEntry`) and in reference to the UI concept (which renders the capabilities as capsule-shaped chips).

## Naming: one lazy chokepoint at turn start

Rather than naming at message-commit time, assign names **at agent-turn start**: scan the log for introduced resources lacking a `bindingName` (pasted capsules — plus, in pre-existing chats, accepted connections from before the agent named its own requests), name them (one quick-model call can batch several), stamp the messages, then build the env. This:

- Puts the pasted-resource naming path in one code site, which also performs lazy seeding of pre-existing chats (above). (New connections never pass through here — the agent names them in `requestConnection` — but legacy connection messages lacking a name do.)
- **Lazily migrates existing production chats** — deployed workspaces are full of unstamped capsule/connection messages; they get names on their next turn with zero upfront migration.
- Makes the crash story trivial: stamped = permanent; crash before stamping just means naming reruns next turn (nothing referenced the name yet).
- Keeps naming off the message-commit path; latency lands at turn start where a timeout + fallback is easy.

**Quick-model call**: prompt with the resource's title + description + names already in scope (seed ∪ chat-local — including names claimed by pending connection requests — ∪ pending assignments); validate as an identifier; dedupe. **Fallback** (quickModel unset, error, timeout, invalid output): the gatekeeper's `describe().suggestedBindingName` + `_2/_3` suffixing — never a deterministic title-derived slug (titles are more verbose than a good identifier; that's why we use an LLM at all). If the target workpiece already has a name in scope, reuse it instead of minting a new one (replaces today's `seenCapsuleGatekeeperIds` index dedupe).

## Env structure

`getEnvForAgent` builds *only* the named entries. Both numeric addressings are **dropped entirely**:

- `env.gadgets[id]` — introduced on this branch, never deployed; no compatibility obligation.
- Numeric capsule slots `env[N]` — these do predate the branch, but: recorded executeCode outputs replay without re-running; after lazy stamping, replayed message text shows `env.NAME` (so the log the model reads is self-consistent); and an ongoing chat's model self-corrects after one undefined-slot error — the same precedent as the flatten removal. The integer-coercion special case in `describeBinding` goes away with the slots.

`getEnvForLoader` (gadget workers) is untouched — `env.GADGET` + own bindings, as always. The migrated default list maps `GADGET → defaultGadgetId`, so in old workspaces the chat env's `env.GADGET` behaves *identically* to how it always did. New multi-gadget workspaces name gadgets via `createGadget`'s `bindingName`.

## Agent tool surface (IDs replaced by names throughout)

No agent tool accepts or requires a workpiece ID anymore:

- **File tools** (`readFile`/`writeFile`/`editFile`): the `workpieceId` parameter (introduced on this branch, no compat obligation) becomes a `gadget` parameter holding the chat's binding name for the target gadget, resolved through the chat binding map (error if the name resolves to a non-gadget). Still optional for replay of pre-branch histories: absent resolves to `defaultGadgetId` as today. Internal keying (read-before-edit tracking, streaming events to the UI, loader caches) stays on workpiece IDs.
- **`createGadget`** gains required `bindingName` (validated as an identifier; description recommends ALL_CAPS style). The name enters the chat-local layer immediately and the workspace default list at **merge promotion** (the default list is derived from non-pending gadget records, so a pending gadget is invisible to other chats' seeds until then). The name is stored on `GadgetRecord` and is **unique across the workspace's gadgets — enforced by a `byBindingName` unique index** on the gadgets collection. Since a pending gadget's record is real, the name is claimed from the moment of creation: a conflicting `createGadget` in another chat (or from the UI) fails with an explicit "name is pending in another chat" error until the first chat's changes are accepted or reverted — the same reservation semantics as pending binding edges — and the name is final from creation, so merge promotion needs no dedupe. Revert/reconcile need nothing beyond deleting the record (which frees the name): the chat-local name dies with the ignored tool call. The recorded tool output keeps `gadgetId` purely for replay bookkeeping (re-adoption/reconciliation need it); agents are never asked to use it and no tool accepts it.
- **`requestConnection`** gains required `bindingName`: the agent knows why it is requesting the resource and should pick the name itself, rather than deriving one from the chosen resource after acceptance. Validated by the shared validator and rejected if the name is already in scope (including names claimed by other pending requests); recorded on the `connectionRequest` message at request time, where it claims the name until denial (see the chat-local layer above). Replay of pre-change histories reads the lazily-stamped name off the message, so the old parameterless shape needs no alias.
- **`saveCapsuleAsBinding` → `setGadgetBinding`**: the agent-visible tool is renamed and generalized — parameters `{gadget: <chat binding name of a gadget>, source: <chat binding name of the resource>, name?: <binding name on the gadget, defaults to source>}`. This is the "wire a resource into a gadget" tool. The added edge is **provisional to the chat** (see "Provisional binding additions" below). For replay compatibility, the **persisted tool-call name in chat logs remains `saveCapsuleAsBinding`**: a small alias table at the record/replay boundary maps the model-visible name to the stored name (and replay additionally accepts the old parameter shape, `capsuleId` etc., whose replay is already a recorded no-op).
- **`removeGadgetBinding({gadget, name})`** — new small tool (new name, no compat concern) so the agent can fully manage a gadget's binding list. (A rename operation can be expressed as remove + set; add a dedicated tool only if models fumble that.)
- **`describeBinding(name)`** — no `gadgetId` parameter (it was introduced on this branch; before that the tool had none, so no back-compat concern). The agent describes *its own* binding by chat env name; if it doesn't hold a binding for a resource, it isn't supposed to access that resource anyway. Integer capsule indices are no longer accepted.
- **System prompt rewrite**: workspace sections are name-first and ID-free (`## Gadget MY_DECK: "Quarterly Deck"`). When enumerating a gadget's own bindings, indicate how each maps into the agent's env, e.g. `STRIPE → your env.PAYMENTS` (matched by target workpiece), or "(no binding in your env)" when the agent holds no name for the target. executeCode/connection/callback descriptions all speak `env.NAME`; `listGadgetInfo`/`AgentGadgetInfo` and `observeUserChanges` observations report names, not IDs.

## Provisional binding additions

Adding a binding to a gadget is a **provisional change**, exactly like gadget creations and code edits: visible only within the originating chat until the user accepts changes (`mergeChanges()`). The mechanism mirrors `GadgetRecord.pending` (Q15) edge-for-edge:

- **`BindingRecord.pending?: {chatId, sequence?}`** marks a provisional edge. The edge is real in the registry so the chat's own preview/test runs see it (`getEnvForLoader` includes it when loading the gadget for that chat's branch); mainline loads, other chats, blueprints (`collectBindingMetadata`), and "use"-role sharing treat it as nonexistent for *reads*.
- **A pending name is reserved to the chat that claimed it.** Because the binding map is keyed by name, a given name can be pending in only one chat at a time — and that's the intended semantics, not just a storage limitation: if a second chat (or the UI acting in one) tries to add the same binding name on the same gadget while it's pending elsewhere, the operation fails with an explicit "this name is pending in another chat" error, until the first chat's changes are accepted or reverted. (Allowing both proposals to coexist would mean accepting both silently overwrites one with the other.) So pending edges are invisible to other chats for reads but still occupy their name for writes.
- **Additions ride the `changes` stream**: the `changes` message gains `addedBindings?: {gadgetId, name, target}[]` alongside `createdGadgets`. The agent tool writes the edge unstamped; `addChatMessages` stamps `pending.sequence` in the same synchronous step that persists the message. Crash recovery reuses the createdGadgets machinery: replay re-adopts unstamped edges backed by persisted tool calls; `reconcilePendingGadgets` generalizes to also reap orphaned pending edges.
- **Merge/revert**: `mergeChanges` clears `pending` on edges with `sequence <= mergeThrough` — which is also the moment the edge becomes visible to the derived workspace default list. `revertChanges` deletes edges with `sequence >= revertFrom`. A binding added to a gadget that is itself pending needs no separate handling on revert (the gadget's deletion takes the edge with it), but ordering is sound either way since the edge's message follows the creation's.
- **UI-initiated binds follow the user-created-gadget pattern**: `GadgetClient.bind`/`bindWithSuggestedName` gain an optional `chatId`; with a chat open (the Connections tab passes the editor's open chat), the bind writes a `changes` message (no-op update + `addedBindings`) and a stamped pending edge in one synchronous step; without, it's immediate and permanent as today.
- **Removals and renames stay immediate** in v1 (a provisional *removal* needs tombstone semantics that don't fit the pending-record shape); documented as an accepted asymmetry — reverting a chat does not restore a binding the agent removed.

## Workspace default binding list

**Not stored — derived on demand** by scanning the gadgets table (which is small, and the list is only *read* at chat creation and lazy seeding), in one helper:

- Two deterministic passes over non-pending gadget records in ID order: first every gadget under its `bindingName` (unique — enforced by the `byBindingName` unique index at creation), then every non-pending binding edge under its edge name (mapping to the edge's target), skipping names already taken. Gadget entries therefore take precedence, and edge-name collisions across gadgets resolve to the lowest gadget ID.
- Renames, unbinds, and workpiece deletions are reflected automatically — no maintenance hooks, no rename propagation, and no migration step (the records the list derives from are written anyway). Chat maps may still hold dangling names from before a deletion; env build skips targets that no longer exist, mirroring the deleted-gadget behavior elsewhere.
- A `defaultBindings` storage singleton was considered and rejected: every write path (creation, merge promotion, rename, unbind, deletion) would have needed an insert/propagate/drop hook to keep a second copy of derivable state consistent. One deliberate policy difference from the stored design: unbinding a gatekeeper's last edge drops it from future chats' seeds rather than leaving a stale entry — more correct (orphaned gatekeepers stop leaking into new chats), and frozen seeds mean existing chats are unaffected either way. If user-curated defaults are ever wanted, a stored overlay can be added later.

**UI-initiated gadget creation**: the quick model names it from the title (same helper as capsule naming; a title→identifier transform is exactly the verbose-to-terse job LLMs are for). The creation dialog gets an *optional* identifier field for users who want to choose the name themselves; when unset and no quick model is configured, fall back to a generic `GADGET`/`GADGET_2`.

## Spawner restricted binding lists

`AgentSpawnerConfig.env: Record<string, WorkpieceId>` — **required** going forward, and explicitly *not* limited to bindings the creating gadget holds: spawners may (and typically will) define bindings of their own, with their own names and targets. No spawn-time name resolution: the config already holds workpiece IDs; `spawnAgent` snapshots it into the spawned chat's `chatContext.bindings` (dropping entries whose targets no longer exist). Spawned agents get only this seed — never the workspace default list — which restores the restriction lost in Part 1.

- Existing spawner gatekeeper records persist the *old* `env?: string[]` allowlist (the field was removed from the type on this branch but survives in stored data). The migration rewrites each spawner's record to the new form (see below). Existing *spawned chats* with a frozen old-style `spawnerConfig` are handled by lazy seeding at turn start (see Seed layer).
- Remove the `TODO(multi-gadget)` markers at api.ts:940 and agent.ts:1612; strike the "allowlists are non-functional" item from Part 1's follow-up list.

### Spawners in blueprints

Blueprints round-trip the spawner config verbatim today (`GatekeeperCreationSpec.agentSpawner.config` → `BlueprintBinding.agentSpawner.config`, collected at overseer.ts:3915-3929, reconstructed via `newAgentSpawnerGatekeeper({...config, modelId})` at server.ts:418-427). That round-trip ends, and **the blueprint binding's `config` property is removed entirely**: workpiece IDs are workspace-local, so a spawner's `env` can't transfer as-is — and once `modelId` (already factored into `suggestedModel` + the user's assignment) and `env` are excluded, the only field left in `config` was `displayName`, redundant with the binding's `title`. The binding stores just `suggestedModel` plus a symbolic env, `Record<envName, SpawnerEnvTarget>` with `SpawnerEnvTarget = {type: "binding", name} | {type: "gadget"}`; instantiation reconstructs the whole `AgentSpawnerConfig` as `{displayName: <binding title>, modelId: <assignment>, env: <resolved>}`:

- **Export** (`collectBindingMetadata`), per spawner env entry: target = the exporting gadget itself → `{type: "gadget"}`; target matches one of the gadget's own binding edges (same workpiece ID) → `{type: "binding", name}` referencing that blueprint binding, so the user never specifies it twice; target bound by no gadget edge → **synthesize an additional top-level blueprint binding entry** for it (named after the spawner env name, described from the target's own `creationSpec` using the same per-variant logic, marked `spawnerOnly: true`) and reference *it* — the user fills it at instantiation time like any other binding, but it is fed only to the spawner, not bound into the gadget. Targets that are other gadgets or other spawners are out of scope for v1 (export fails with a clear error).
- **Instantiation** (`newGadgetFromBlueprint` and the agent's blueprint path): create gatekeepers for all non-spawner bindings first (binding the non-`spawnerOnly` ones into the gadget), then create each spawner with the reconstructed config — `displayName` from the binding's title, `modelId` from the assignment, and `env` resolved: binding references → the just-created gatekeeper IDs, `{type: "gadget"}` → the new gadget's ID.
- **Existing blueprints in KV: compatibility deliberately broken.** Mapping the old shape at read time would require intentionally coercing types to sniff `config.env: string[]` — ugly — for a product still in early testing with nearly no agent-spawner blueprints in the wild. Instead, old blueprints containing agent spawner bindings will not function correctly after this change; that's fine. (Workspace-*storage* spawner records are unaffected — the DO migration still rewrites those, where the data is authoritative rather than a copyable template.)

## Migration

The 0→1 migration has **not been deployed**, so these steps are folded into it directly rather than adding a new version (dev machines already at v1 will have gadget records lacking `bindingName` — acceptable for throwaway dev data):

- The legacy gadget record gets `bindingName: "GADGET"`. The default binding list needs no step of its own (it is derived, not stored): that record plus the binding edges the migration already creates yield exactly the old flat env — each named gatekeeper under its old binding name, plus `GADGET → defaultGadgetId`.
- Rewrite each agent-spawner gatekeeper record. The config appears in **two places** and both must be updated:
  - `creationSpec` (`{type: "agentSpawner", config}`): rewrite `config.env` — old `env: string[]` allowlist → `Record<name, WorkpieceId>` by resolving each name against the gatekeepers' `bindingName`s; an *absent* old allowlist (historically meaning "unrestricted") → all named gatekeepers plus `GADGET → defaultGadgetId`, preserving old behavior.
  - `class`: the old config is baked into the class stub's props (`AgentSpawnerBindingProps`), which can't be edited in place — **recreate the stub** via `ctx.exports.AgentSpawnerGatekeeper({props})` with the migrated config, exactly as `newAgentSpawnerGatekeeper` does (overseer.ts:6148-6168). All inputs are on hand (`overseerId` = the DO's own ID, `config` = the migrated one) except `creatorUserId`, which isn't recoverable from the record — omit it and rely on the existing legacy fallback to the workspace owner (already the documented behavior for pre-`creatorUserId` bindings).
- **Bugfix (independent of this feature): wrap the whole migration in `ctx.storage.transactionSync`** so a mid-migration error can't leave a workspace half-migrated.

## Name validation

One shared validator, applied at every chokepoint that writes a binding name (`bindWorkpiece`, default-list writes, chat-name stamping, spawner config acceptance, the client `bind()` path, and the agent tools): the name must be a **valid JavaScript identifier** (identifier regex + not a reserved word), and must not be a **dangerous or confusing property name**: reject anything that exists on `Object.prototype` (`name in Object.prototype` — covers `__proto__`, `constructor`, `hasOwnProperty`, `toString`, `valueOf`, the `__defineGetter__` family, etc.) plus `prototype`. These names would collide with inherited object members (or worse, mutate the prototype chain) anywhere a binding map is used as a plain object. ALL_CAPS is *style guidance only*, recommended in tool descriptions and used by our own generated names (`PARAMS_<N>`, suggested binding names) but not enforced — today's ALL_CAPS regex in the agent tool (agent.ts:1963) is relaxed accordingly. Reservations stay minimal: `GADGET` remains reserved in *gadget* binding maps (it's auto-injected there); chat maps may freely contain `GADGET` — that's the point.

## Resolved decisions

1. **Numeric `env[N]` slots: dropped entirely**, relying on recorded-output replay + one-error self-correction for ongoing production chats.
2. **Names are validated as JS identifiers** (minus reserved words and `Object.prototype`/`prototype` property names); ALL_CAPS is convention, not law.
3. **Callback bindings are named `PARAMS_<N>`** (they are bindings, so they follow the ALL_CAPS convention), deduped against names in scope.
4. **`saveCapsuleAsBinding` is renamed to `setGadgetBinding` for the agent**, while chat logs keep recording the old name via an alias at the record/replay boundary.
5. **Spawner env is a `Record<name, WorkpieceId>`**, required, independent of any gadget's bindings; existing spawners are migrated (allowlist resolution, absent = unrestricted = everything), including recreating the baked-props class stub.
6. **No new migration version** — the un-deployed 0→1 migration absorbs the new steps, and gains `transactionSync`.
7. **Binding additions are provisional to the chat** (`BindingRecord.pending` riding the `changes` stream, visible to the derived default list once merged); a pending name is reserved to its claiming chat (colliding proposals from other chats error) until accepted or reverted; removals/renames stay immediate in v1.
8. **Blueprints store spawner envs symbolically** (`{type: "binding", name}` / `{type: "gadget"}`), sharing user-filled bindings with the gadget where targets coincide and synthesizing `spawnerOnly` bindings where they don't. The binding's `config` property is removed entirely — after factoring out `modelId` and `env`, only `displayName` remained, redundant with the binding `title` — an accepted compatibility break with the few existing agent-spawner blueprints.
9. **`requestConnection` names its own binding**: `bindingName` is a required tool parameter (the agent knows why it wants the resource), recorded on the `connectionRequest` message at request time and claiming the name in the chat's scope until acceptance or denial — quick-model naming applies only to pasted resources and legacy pre-change messages.
10. **The default binding list is derived, not stored**: reconstructed on demand from non-pending gadget records (`bindingName` + binding edges) with a deterministic precedence rule, eliminating the `defaultBindings` singleton and all its maintenance hooks; unbinding consequently drops orphaned gatekeepers from future chats' seeds (frozen seeds keep existing chats unaffected).
11. **Gadget `bindingName`s are unique workspace-wide**, enforced by a `byBindingName` unique index on the gadgets collection. Because pending records are real registry records, a provisional gadget reserves its name from creation — a conflicting creation in another chat errors until the claiming chat's changes are accepted or reverted, mirroring pending binding edges — and merge promotion needs no suffix dedupe (the record's name is final from creation).
