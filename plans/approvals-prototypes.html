Workshop · approvals

Keeping a chat’s changes, and letting changes go ahead

Two things wait for a person in the Workshop. They look alike, but they carry different risks, so they get different defaults. This page sets out what is built and what is proposed, with three prototypes to try.

A chat’s changes to its gadgets

Code. Each chat works like a branch: it proposes, and keeping puts the changes into what everyone uses.

  • Undoable in one click
  • Nobody outside the workspace sees them
  • Default: kept without asking

A connection’s changes to the world

A Doc edited, a message sent, a slide moved. Decided one action at a time.

  • Some can’t be taken back
  • Other people see them
  • Default: asks first, unless you said otherwise
Built · prototype 1

Chats are kept as they finish

Before this, a chat was held back whenever another chat had changes waiting for the same gadget. Someone running two chats on one tracker was asked about both, at no risk to either. Now the first chat to finish is kept. When the second finishes, it brings in what the first kept, and is kept on top of it if that merges cleanly. Nobody sees the words merge, branch or conflict unless two chats changed the same lines.

Still asks for: a conflict, named by file; a binding, blueprint update or bring-in the user asked for, which are theirs to decide; and a workspace someone else is in, whose work in progress keeping could overtake.

Built · prototype 2

Every account gets a page, and standing permissions live there

The manage dialog becomes a page per connected account. It leads with what the account may change without asking. Reading never asks. Each workspace that uses the account gets one group, with a row per kind of change and a plain choice: Ask first or Automatic. “Always approve” on a request writes the same rule and says this page is where to change it.

Labels come from the gatekeeper (“Slide text edits, in any presentation this connection reaches”) and split at “, in ” into the change and how far it reaches. A workspace that has read sensitive data asks before every change whatever is chosen, and says so.

Proposed · prototype 3

A default for the account, overridden per workspace

“Doc edits can go ahead” is really a choice about your Google account, not about one workspace. The proposal adds one row above the workspaces. New workspaces follow it, and a workspace can differ from it.

Kernel change it needs

  • Record which account a connection came through (GatekeeperCreationSpec.accountId; ambient connections already do).
  • Keep a per-account set of automatic kinds in the user’s object.
  • Seed a workspace’s rules from it when the user connects that account there.

Not built yet. It adds a mechanism beside the existing rules and changes who owns a rule in a shared workspace, so it should go past a kernel reviewer first.

Considered and left out

What isn’t offered, and why

An Auto switch per chat or per gadget

The kernel supports both. Offering them would give a second and third place to look when something went ahead unexpectedly. A rule already covers “stop asking me about Doc edits”, and it can be seen and taken back on the account page.

The agent resolving conflicts on its own

It could, since the conflict markers are in its files. But the user would then keep code that neither of them looked at. The question names the files, and asking the agent to combine them is one message away.

The rule of thumb: keep code without asking, because it’s yours and it’s undoable. Ask before anything reaches the world, unless you chose otherwise in one place you can find again.
