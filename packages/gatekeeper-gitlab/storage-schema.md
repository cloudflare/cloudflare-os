# GitLab gatekeeper storage schema

Durable Object storage layout for `UserAccount` and `GitLabGatekeeperImpl`. Written from the code
as each piece lands; the GitHub gatekeeper's `storage-schema.md` is the shape this mirrors.

## UserAccount

| Key | Value | Notes |
|---|---|---|
| `callback` | `Fetcher<GatekeeperConnectCallback>` | Stored at connect; used for `complete`, `reconnectComplete`, `credentialsExpired`. |
| `nonce` | kit `connect-handshake` record: `{ value, expiresAt, stage: "initiation" \| "oauth" }`, plus at the `oauth` stage `{ codeVerifier, redirectUri, startedUnder, reconnect }` | Two-stage connect nonce, consumed by the callback (or by GitLab's refusal). `codeVerifier` is the PKCE verifier; `redirectUri` the `redirect_uri` the authorize request carried (the stable Worker's, on a preview), repeated verbatim in the code exchange; `startedUnder` the connection generation the attempt began under; `reconnect` whether the grant is staged rather than made live, fixed when the attempt starts. |
| `requestedScopes` | `string[]` | Scopes requested for this flow (auth-only or full). |
| `ephemeral` | `boolean` | Auth-only sign-in grant; self-destructs two minutes after `complete()`. |
| `credentials` | `{ accessToken, refreshToken, expiresAt, scopes }` | The live grant, owned by the kit's `CredentialCoordinator` with its `credentials:*` keys (identity fence, connection generation, recorded death, migration marker). `expiresAt` is epoch ms from the token response's `expires_in`; the coordinator refreshes a minute before it, redeeming the single-use refresh token once and storing the rotated pair before serving either. `scopes` are the scopes requested at grant time (the token response carries none); empty on a stub-era grant, which is the reconnect trigger. |
| `accessToken`, `accessTokenExpiresAt`, `refreshToken`, `scopes` | | The layout before the kit, which the deployed internal stub also wrote (minus `scopes`): migrated into `credentials` on first read, then deleted. A missing expiry refreshes on first use. |
| `user` | `{ id, generation }` | The GitLab user behind the connection, read from `GET /user` on first need (the observer probe) and trusted only while the connection generation is unchanged. |
| `expiredNotified`, `expiredNotifiedArm` | kit `credential-expiry` latch | `credentialsExpired()` sent once per dead grant: latched after the Workshop acknowledges, re-armed by every credential replacement. |
| `stagedCredentials` | kit `credential-stage` record of `{ grant, startedUnder }` | A reconnect's grant and the connection generation it replaces, until `commitReconnect(stageId)`. Once another reconnect has moved the generation, the commit revokes the staged tokens instead. |
| `cache:@access:*` | kit `KvTtlCache` | This account's own answers about project access, keyed by `project/<projectId>` subresource (with `/role/developer` or `/role/maintainer` for the role it names) and partitioned by the connection generation, which every connect, reconnect and disconnect replaces: its `members/all` probe by the project's id, asked when it observes another's binding. A grant is reused for 15 minutes and a denial for 15 seconds, and only while the grant is live: the partition is read through it on every use, so a disconnected or confirmed-dead grant fails the check instead. A failure to answer is never stored. |

## GitLabGatekeeperImpl

KV only. Three families: a TTL cache that any queued/applied/rejected action invalidates wholesale
(one generation counter, not a sweep), the cache of finished CI job logs (`ciLog:*`, its own TTL
and size budget, outside the generation: no action changes a finished log), and durable state
that survives cache clears.

| Key | Value | Notes |
|---|---|---|
| `projectId` | `number` | The bound project's GitLab id, read once from `/projects/<encoded path>` (whose redirect, for a moved project, is never followed). Every REST request beneath the project is then sent beneath `/projects/<projectId>`, git fetches and pushes go to the path that id has now (read by id before and after each), and every read reports `project/<projectId>` as its subresource, or that with the role CI data needs. Absent until first use, and nothing is read or written until it is stored. A binding that read before ids were pinned was pinned to whichever project its path named at its first read since. |
| `cachesByProjectId` | `true` | Set once the caches hold only what was read by the pinned id. A binding without it may hold reads a release that addressed the project by path made, from whichever project had the path then, so on start `cacheGeneration` is moved, invalidating every `cache:*` entry, `observerRoster` is deleted, and this is set. `ciLog:*` stays, since each log is revalidated by job id beneath the pinned project before use. |
| `cacheGeneration` | `number` | Bumped by `#clearCaches()`; every `cache:*` entry records the generation it was written under and is ignored once it differs. |
| `cache:<kind>:<parts…>` | `{ fetchedAt, value, generation }` | TTL cache. Families: `version` (1 h); `viewer` (5 min); `project-raw`, `project-by-id`, `issue`, `mr-raw`, `mr`, `mr-approvals`, `discussions`, `compare`, `commit-raw`, `branch-head`, `mr-diffs`, `mr-simulated`, `pipeline`, `job` (30 s); `list-issues`, `list-mrs`, `list-branches`, `list-tags`, `list-commits`, `mr-commits`, `mr-pipelines` (15 s); `merge-base` and `ci-config` (never expire -- pure functions of their shas: `ci-config:<sha>:<path>` is whether the CI configuration file exists at that commit). `project-raw` and `commit-raw` hold GitLab's responses as returned, normalised on each read (an earlier version cached normalised data under `project` and `commit`; those entries are never read again and expire). `mr-diffs` pages are keyed by the merge request's whole revision (`baseSha`, `mergeBaseSha`, `headSha`): the target branch can move under an unchanged head. CI status is never served from these: `pipeline` and `job` serve the opens' checks, while `getDetails()` re-reads them (refreshing the entry), and a log read re-reads the job too, since its status says whether the log is final and `erased_at` whether it may be served; pipeline listings, push events and test reports are not cached. A merge request's `getDetails()` re-reads it for `ci`, refreshing `mr-raw` and dropping an `mr` entry cached at an older head. `mr-pipelines` holds a merge request's pipeline rows (id, project, commit; at most 1000), which decide the pipelines and jobs its binding may open; one not in the cached rows is looked for once more in a fresh listing before it is refused, and `listPipelines()` on the merge request pages uncached. No ETags: GitLab REST does not reliably answer conditional requests. |
| `counter:<name>` | `number` | Action ids (`action`) and provisional ids: `resource` (`~N`), and `comment`/`review`/`diff`/`reply` (`~comment1`, …). |
| `action:<approvalId>` | `{ action, state: "staged" \| "pending", progress?, … }` | A queued action; `#listPendingActions()` reads the `pending` ones and the read side overlays them. A `push` record binds `{ branch, expectedOldSha, newSha, force }` at queue time, with `targetProtected` (whether the branch is the default or a protected one, which the submit-time auto-approval verdict reads, and apply checks again for a push it left unprotected; absent on older records), a `createIssue` or `createMergeRequest` record its resolved `assigneeIds` and `assigneeIsBot` (whether any assignee is a bot or service account, which only the submit-time verdict reads; absent on older records), and a `mergeMergeRequest` record its `expectedHeadSha` and, for a source branch in this project, `sourceBranch`: rejecting a push retires the queued pushes and merges bound to the heads it strands. `progress` records how far a review's apply has got, so a retry resumes instead of repeating a step: `approval` (`"approving"`, `{ approvedAt }`, or `"preexisting"`), `comments` (per diff comment: `null`, `"creating"`, its draft id, `"published"`), `requestedChanges`, `summary` (the note id, once posted). A step whose answer can be lost is recorded as under way first, and the retry asks GitLab what became of it -- save the summary, which is posted again; a discard reads it to take back what is still unpublished, best-effort: a cleanup GitLab refuses does not keep the action pending. |
| `retiredAction:<approvalId>` | `{ action, state: "approved" \| "rejected", appliedAt?, rejectedAt?, revertInfo?, progress? }` | An action past its lifetime, kept for revert. |
| `provisional:<~N>` | `{ kind, realId? }` | A provisional issue or merge request and, once created, its real number. Both `#~N` and `!~N` resolve through it, each against its own kind. |
| `diffAlias:<~id>` | `string` | A provisional reply's real note id, once the reply is posted; a reply queued against it while it was pending resolves through this. |
| `ciPushApplied:<sha>` | `number` (epoch ms) | When this gatekeeper applied a push that made `<sha>` a branch head: CI's first "became the head" source, ahead of the merge request's diff versions, the commit date, and GitLab's push events. Only the 10-minute CI start window reads it, so each new record first prunes those older than that, and the family is capped at 100 (oldest dropped). A retried apply keeps the first record. |
| `ciLog:meta:<jobId>` | `{ version: 1, firstLine, totalLines, lineCount, chunks, bytes, storedAt }` | A finished job's normalised log (the kit's `CiLogCache`; the binding is one project, so the job id names it). Written only once the job's phase is `done` and GitLab returned a log. Expires an hour after `storedAt`. Every `readLog()` re-reads the job first: one gone or erased (`erased_at`) deletes the entry and the read fails. A hit is served only while the connected account holds Developer (30) on the project (debug traces are Developer-only, the job read Reporter's); otherwise the read fetches `/trace` and GitLab decides. |
| `ciLog:chunk:<jobId>:<index>` | `string` | The log's retained lines, newline-joined, in chunks of at most 512 KiB (two bytes per character); `<index>` is zero-padded to six digits. A missing chunk drops the whole entry. |
| `ciLog:age:<storedAt>:<jobId>` | `string` (the job id) | Eviction index, oldest first (`storedAt` zero-padded to 16 digits). A store sweeps expired entries, then evicts the oldest until the new log fits. |
| `ciLog:totalBytes` | `number` | Bytes held across every `ciLog:chunk:*`, against a 32 MiB budget; a log larger than the budget is not stored. |
| `observedSet:<set>` | `"pending" \| "observed"` | The CI-data gate releases before reads reported subresources kept (the kit's `ObserverTracker`, two tracked sets): marked by the first read of its set, `ci-logs` by a job-log read or a test-report read whose connected account was below Maintainer, `ci-test-reports` by a test-report read whose account held Maintainer (40). Reads no longer mark either. While a set is present, `addObserver` requires its role, Developer (30) for `ci-logs` and Maintainer for `ci-test-reports`, on both the pinned project and the one the binding's path names. |
| `observer:<id>` | `Fetcher<GitLabVerifierApi>` | An admitted observer's verifier, which the tracker stores and caps at 50; no read checks them any more. `removeObserver` deletes it. |
| `observerRoster` | `"complete" \| "legacy"` | Written by releases that refused CI-data reads on a binding created before they stored observers. Deleted on start (see `cachesByProjectId`); nothing reads it. |
| `observer-attempt:<id>` | `{ verifier, at }` | The tracker's record of an admission in flight; swept after 10 minutes. |
| `observer-nonce:<id>` | `string` | Fences that attempt: `removeObserver` deletes it, which cancels the admission wherever it is parked. |

The kit reserves the `observer-withhold-fence:*` and `observer-withhold-latch` keys for owner-only
reads; this gatekeeper has none, so they are never written.
